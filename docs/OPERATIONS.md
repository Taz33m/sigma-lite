# Operations Runbook

SigmaLite's public-beta posture assumes:

- Frontend on Vercel or equivalent static hosting.
- Backend on Render or equivalent FastAPI service.
- PostgreSQL for `DATABASE_URL`.
- Redis for distributed rate limiting.
- `api.<domain>` proxied through Cloudflare before it reaches Render.

## Health, Logs, And Metrics

- Use `/health/live` for process liveness.
- Use `/health/ready` for Render health checks because it verifies database connectivity.
- Use `/metrics` for lightweight Prometheus-style request counters and latency totals.
  Local/test expose it publicly; staging/production require `METRICS_TOKEN` or
  explicit `EXPOSE_PUBLIC_METRICS=True`.
- API docs (`/docs`, `/redoc`, `/openapi.json`) are enabled locally but hidden
  in staging/production unless `EXPOSE_API_DOCS=True`.
- Backend request logs are structured JSON and include `request_id`, `CF-Ray`, `Rndr-Id`, method, path, status, duration, actor id, and client host.
- Set `ENABLE_OTEL=True` only when OpenTelemetry FastAPI instrumentation is installed in the runtime image.

Render setup:

- Configure the service health check path to `/health/ready`.
- Use Render logs or log streams for request/application logs.
- Use Render metrics/metrics streams for CPU, memory, request, and disk visibility where the plan supports it.
- `render.yaml` defines the `sigmalite-api` web service plus managed Postgres
  and Redis resources. The service runs Alembic migrations before starting
  Uvicorn.
- Fill `ALLOWED_ORIGINS` in the Render Dashboard with the deployed frontend
  origin, for example `https://<frontend-domain>`.
- `SECRET_KEY` is generated by the Blueprint. Rotate it manually if it is ever
  exposed.
- Set `METRICS_TOKEN` if an external scraper needs `/metrics`; otherwise leave
  metrics hidden at the app layer and use Render/Cloudflare telemetry.
- The default Blueprint stores uploaded source CSV artifacts under `/tmp`.
  DB row/cell storage remains authoritative after ingest, but attach durable
  storage or move artifacts to object storage before promising source-file
  retention.

Blueprint deploy flow:

1. Commit and push `render.yaml` to the GitHub/GitLab/Bitbucket remote.
2. Open `https://dashboard.render.com/blueprint/new?repo=https://github.com/Taz33m/sigma-lite`.
3. Review the `sigmalite-api`, `sigmalite-postgres`, and `sigmalite-redis`
   resources.
4. Set `ALLOWED_ORIGINS` to the frontend origin.
5. Apply the Blueprint and wait for the first deploy to become live.
6. Point Cloudflare `api.<domain>` at the Render API custom domain and set
   `VITE_API_URL=https://api.<domain>` in the frontend environment.

Vercel frontend setup:

- Set the Vercel project root directory to `frontend`.
- `frontend/vercel.json` builds the Vite app and rewrites SPA routes to
  `index.html`.
- Set `VITE_API_URL=https://api.<domain>` in Vercel.
- Set `VITE_WS_URL=wss://api.<domain>` only if the WebSocket origin differs
  from `VITE_API_URL`.

## Backups And Restore

Primary path:

- Use managed PostgreSQL backups/PITR on the hosting plan.
- Keep uploaded CSV artifacts on durable storage or a persistent disk.
- Run `alembic upgrade head` before serving restored traffic.

Fallback `pg_dump` path:

```bash
pg_dump "$DATABASE_URL" > sigmalite-backup.sql
psql "$RESTORE_DATABASE_URL" < sigmalite-backup.sql
```

Restore smoke:

1. Point backend env vars at the restored database.
2. Run `cd backend && uv run alembic upgrade head`.
3. Check `/health/ready`.
4. Register/login, upload CSV, create sheet, edit cell, sort/filter, aggregate, comment, export CSV/XLSX/PDF, and connect WebSocket.

## Staging API Smoke

Run the deployed public-beta API smoke after each staging deploy or restore. The
script creates a unique user and dataset, patches a versioned cell, creates a
comment and chart, exports CSV, and prints a compact JSON summary.

```bash
cd backend
SIGMALITE_API_URL=https://api.<domain> uv run python load/staging_smoke.py
```

Or pass the base URL explicitly:

```bash
cd backend
uv run python load/staging_smoke.py --api-url https://api.<domain>
```

## Cloudflare API Protection

Recommended DNS:

- `api.<domain>` is proxied through Cloudflare and points to the Render backend custom domain.
- Frontend sets `VITE_API_URL=https://api.<domain>`.
- Frontend may set `VITE_WS_URL=wss://api.<domain>`; otherwise it derives WebSocket URLs from `VITE_API_URL`.

Initial WAF/rate-limit rules:

- `/api/auth/*`: strict rate limit and bot/challenge mode before block mode.
- `/api/datasets` uploads: lower request rate and body-size monitoring.
- `/api/sheets/*/export`: per-user/IP rate limits.
- `/api/*`: broader safety rate limit.

API Shield note:

- FastAPI currently emits OpenAPI `3.1.0`.
- Generate a checked OpenAPI `3.0` artifact before uploading schema validation rules:

  ```bash
  cd backend
  uv run python load/export_openapi_30.py --output /tmp/sigmalite-openapi-30.json
  ```

- Start schema validation in log mode before switching any high-risk rule to block.

## App Rate Limits

The backend uses Redis sorted-set sliding windows in production
(`RATE_LIMIT_BACKEND=redis`). Local/test can use `auto` or `memory`; `auto`
falls back to in-memory sliding windows when Redis is unavailable.

Defaults:

- Auth: 20/min/IP.
- Auth identity: 10/min per username/email.
- Upload: 10/min/user plus 60/min/IP safety bucket, with IP fallback for unauthenticated requests.
- Export: 10/min/user, with IP fallback for unauthenticated requests.
- Query: 300/min/user, with IP fallback for unauthenticated requests.
- Cell edits: 120/min/user.
- Formula previews: 60/min/user.
- Comment/chart/share/sheet mutations: 60/min/user.

Blocked requests return `429` and write `rate_limit.blocked` audit events with
the limiter scope, path, method, limit, and window size.

For production, set:

```env
RATE_LIMIT_BACKEND=redis
REDIS_URL=<managed redis url>
```

## Large Dataset And Load Testing

Generate deterministic CSVs:

```bash
cd backend
uv run python load/generate_dataset.py --rows 100000 --output /tmp/sigmalite-100k.csv
uv run python load/generate_dataset.py --rows 250000 --output /tmp/sigmalite-250k.csv
```

Run the Locust scenario after installing Locust in your local/staging environment:

```bash
cd backend
locust -f load/locustfile.py --host http://127.0.0.1:8000
```

The Locust flow registers, uploads, creates a sheet, then exercises sheet-scoped
query, filter/sort, aggregate, edit, comment, and export paths.

Run the lightweight local API benchmark:

```bash
cd backend
uv run python load/benchmark_dataset.py --rows 100000
```

To turn local/staging page query, filter/sort, and aggregate targets into a
nonzero-exit gate:

```bash
cd backend
uv run python load/benchmark_dataset.py --rows 100000 --assert-targets
```

Do not publish benchmark numbers until they are rerun against the target
staging stack. Keep local runs useful for regressions, but treat staging
Postgres, Redis, upload storage, and API-edge behavior as the source of truth
for public claims.

Public-beta targets:

- 100k-row page query p95 under 500ms.
- 100k-row sort/filter p95 under 1.5s.
- 100k-row aggregate p95 under 2s.
- No 5xx under 10 concurrent users for 5 minutes.

Keep CI on the 10k smoke test; run 100k and 250k only locally or in staging.

## Incident Checklist

1. Check `/health/ready`, Render service events, and recent deployment.
2. Inspect structured logs by `request_id`, `CF-Ray`, status, and duration.
3. Check database connection count, storage, and slow queries.
4. Check Cloudflare WAF/rate-limit events for blocked or challenged traffic.
5. If data integrity is suspected, stop writes, snapshot the database, and restore into a separate database before switching traffic.
